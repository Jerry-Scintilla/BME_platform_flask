# 独立项目与项目日历部署交接

独立项目拥有固定编号、长期团队、研发节点和D0，营期通过关联组织项目。本次结构与旧营期读取互相配套，必须先执行迁移79，再发布后端和前端。关闭新入口不意味着可以省略结构迁移。

## 发布基线与范围

前后端均在 `feature/camp-group-core` 的独立检出目录开发，基于前端 `390ed3a`、后端 `ed40f70`。积分开发目录保持原样。实际服务器版本在部署时核对，本地版本不代表已部署。

新入口 `/my-projects` 与 `/project-workspace/:projectId`。公开项目广场 `/projects/:id` 保留原语义。旧营期URL和节点通知通过服务器映射进入对应项目及本期关联；尚未映射的项目继续走原路径。

## 部署顺序

1. 记录服务器维护分支、前后端提交、生产环境配置与当前静态资源目录。按现有部署流程备份业务数据库、附件目录或对象存储、静态产物和环境配置。保留服务器其他任务的文件与变更。
2. 核对既有迁移72至78，尤其是组织核心与身份外键。先运行 `python scripts/migrate/migrate_79_project_core.py` 查看DDL，再对已确认的目标库运行 `python scripts/migrate/migrate_79_project_core.py --apply`。79仅建立独立项目的新表，支持重复执行；不自动合并项目、复制成员、回算评分或发放积分。现有应用启动时的 `create_all()` 不能替代发布前的迁移核对。
3. 发布配套后端。`PROJECT_CORE_ENABLED` 默认关闭；确认结构、身份与存储配置后，先在灰测环境或指定灰度流量设置为 `true`。部署用户端与管理端的生产构建；本地预览端口和演示账号不作为生产启动方式。
4. 用获准的负责人、成员、老师账号验证独立项目创建、日历、记录、附件、本期关联和只读范围。项目负责人身份沿用现有任职核验策略，普通成员沿用人员与主参与账号规则；本次不在生产降低身份门槛。
5. 存量迁移先只读预览，再逐项目准备映射与切换。核对成员、负责人、原节点及材料数量和源版本摘要。跨届同名不自动合并；负责人、人员或账号冲突保留在待处理清单中。
6. 验证积分仍使用原营期ID、奖励来源与幂等键，培训营仍使用原教学流程。上述检查只覆盖本次修改及直接依赖，不执行全量回归。

## 只读预览与按项目切换

从服务器当前后端目录、现有生产环境中运行。下列ID和摘要应取自实际预览结果。

```sh
python scripts/project_core_migration.py --unit-id UNIT_ID --actor-id ADMIN_ID
```

预览不提交业务修改。仅在核对后使用独立的命令准备和切换：

```sh
python scripts/project_core_migration.py --unit-id UNIT_ID --actor-id ADMIN_ID --action prepare --apply --source-digest SOURCE_DIGEST --reason '核对后的迁移依据'
python scripts/project_core_migration.py --unit-id UNIT_ID --actor-id ADMIN_ID --action switch --apply --source-digest SOURCE_DIGEST --reason '核对一致后切换'
```

关联到已经存在的长期项目时，准备命令增加 `--project-id PROJECT_ID`。新的有效参营人员必须属于该长期团队；历史成员不自动变成当前团队成员。

本轮存量切换只接受尚未结营、组织已映射且有效的项目。既有已结营档案继续由原营期入口读取，迁移工具会拒绝改写其冻结归属；如需把这些旧档案统一关联到长期项目，另行核对档案中的原始人员、节点和修正版本后再实施。新模型建立的本期关联在结束时冻结，不能在同一营期内重开覆盖。

准备后若源数据变化，重新预览并撤销尚未切换的准备映射，再重新准备。`cancel` 同样需要 `--apply`、当前源摘要和原因。已切换项目不通过删除映射回退。管理端和用户端管理员的迁移界面调用相同的服务与摘要校验。

## 必须核实的业务边界

- 一个项目可以不参加任何营期，也可关联多个不同营期；项目编号和D0沿用。
- 本期名单是显式参营关系。退出本期不退出长期团队；退出长期项目会结束相应有效参营参与，担任本期负责人时先完成交接。
- 研发完成与营期考核完成分别管理。原0分、单人管理员验收、多人成员评价、材料版本和原ID保留。
- 本期结束冻结本期资料、人员与考核。后续研发记录不改写已冻结内容；营期老师不自动获得整个长期项目的权限。
- 个人考核材料仍按原授权读取，附件短签在下载时重新核验；长期项目共享记录的附件是另一种明确范围。
- D0修正先预览，移动未来相对计划；固定日期、实际发生日期和冻结历史不随之移动。已完成计划修改日期需先显式重开。

## 项目提醒

提醒任务没有自动加入生产调度，不随日历读取或应用启动写通知。新功能开关关闭时任务不发送。

```sh
python scripts/run_project_reminders.py
python scripts/run_project_reminders.py --days 3
```

以上默认只读预览。需要写入站内提醒时显式增加 `--apply`，按既有服务器调度体系安排；按来源、接收人和日期去重，不操作积分。调整日期后旧日期不再产生新提醒，已经发送的通知作为历史保留。

## 回退与退役

未切换存量项目、也未产生独立项目数据时，可按常规流程回退配套版本。产生新写入后，应保留本次兼容后端与结构，通过关闭新入口或恢复兼容界面控制灰度；已映射项目的长期成员写入继续由新事实源管理。

任意旧后端不了解项目映射和写入护栏，不能在新数据上重新开放旧成员写入。必要时暂停受影响项目的写操作。若需恢复数据库或附件备份，先停止写入并清点备份后的新增记录，按既有一致恢复流程处理。

当前保留未迁移项目和培训营的兼容读取。服务器灰测、实际存量切换和观察通过后，再单独安排旧字段清理和完全退役；本地检查不等于这些生产步骤已经完成。
