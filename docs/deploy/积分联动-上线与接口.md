# 训练营积分联动

分支：`feature/points-integration`。前后端分别开发，不修改商城部署或真实积分。

## 实现范围

- 顶栏余额、头像积分摘要、个人中心「我的积分」、移动端入口。个人积分展示平台常驻获取途径和已到账收支；未配置奖励的任务标记待开放，不产生发放。
- 余额只读积分中心；未关联、身份待核验、查询失败均不伪装为零分。
- 现有商城一次性票据登录复用，不保存票据或放进 URL。
- 规则按营期与奖励类型配置，追加不可覆盖的版本；积分事件保留当时的分值和规则版本。
- 每日承诺考勤按既有 `_eval_day` 结算，次日发放；迟到但时长达标仍采用原有达标口径。按周考勤没有统一达标门槛，不套用每日规则。
- 章节认证与奖励入队在同一事务；同一学员同一章节跨营不重复。撤销认证同步登记取消或反向扣减；改分不重复奖励。定时扫描补偿遗漏。
- 贡献、结业奖励由导生提报，老师审批；老师可提报并由其他老师或超管审批。不能自提自审或审核自己的奖励。结业需营期日期结束且尚未归档。
- 管理端入口：平台运营 → 积分管理；营期老师与导生在当前营期工作台的「积分奖励」中处理提报与审核；学员在「营期积分」中查看本营规则和发放进度。工作台不提供跨营切换器。
- 提报依据、审核、入账、重试、撤回记录均保存。幂等键在首次外部请求前持久化，响应未确认时不记为到账。

## 平台级规则与文章先审后发（2026-10-15，迁移 81）

- 平台规则 `camp_id` 为 NULL：`daily_checkin` 每日打卡、`community_post` 每日首帖、`article` 文章过审。仅管理员经管理端「积分管理 → 平台」配置；MySQL 命名锁防并发插重。
- 每日打卡：按 CheckRecord（验证码/人脸通道，不挂营期）按日聚合已签退段时长，D 日在 D+1 04:00 后结算；金额 = 基础分 + 每满 N 小时（默认 2）× 每次加分（默认 1），封顶可配。event_key=`checkin:{uid}:{date}`。
- 每日首帖：worker 扫 DiscussionThread（非 deleted）按（作者, 日）去重入队，不走发帖事务钩子。event_key=`community_post:{uid}:{date}`。
- 文章过审：v2 文章普通用户发布进 pending_review（先审后发），文章管理员（super_admin + article_management）直发；审批 `POST /v2/article/admin/<id>/review` 行锁防并发，通过时入队，"每日第一次"按提交送审日计。event_key=`article:{uid}:{submitted_date}`。
- 待审文章仅作者/管理员可见（详情/列表/feed/收藏/评论区全部收敛）；驳回回草稿保留 reject_reason 并通知作者；审核通过后作者仍可自由编辑不重审（用户拍板）；v1 `/article/public` 普通用户 403 收口。
- 身份不合格（无教育邮箱）发放落 `blocked` 不自动重试，管理端「入账异常」可手动重试（用户补验后）。
- 已知叠加：同一份 CheckRecord 若同时配置营期考勤规则与平台打卡规则会双份积分，配置时知悉；effective_at 不可回填 = 不追溯赠分。
- `/points/tasks` 返回真数据卡（含 `done_today`），平台 items 不含 camp 字段；首页右侧栏挂积分任务面板（未配置或未登录整块隐藏）。

个人常驻目录使用 `/points/tasks`；本营规则和个人进度使用 `/points/camps/<sid>/tasks` 与 `/points/camps/<sid>/rewards`，始终校验当前用户与营期关系。旧 `/points/pending` 必须指定 `camp_id`，不再提供个人中心的跨营待办。管理元数据接受 `camp_id` 并校验授权，个人余额接口不再返回营期管理资格或待办汇总。

## 已核实的积分中心契约

2026-10-14，通过 `172.25.56.83:2222` 服务器只读获取 `192.168.1.196:18081/openapi.json`。
训练营线上路径为 `/BME_platform_flask_v2` 与 `/root/bme-platform-frontend`，已核对远端仓库映射；Notebook 与 3D 农场仅作为接入参考，未作为训练营修改目标。

- `GET /platform-api/v1/users/{platform_user_id}/points`：余额、中央用户 ID、平台用户 ID、邮箱。
- `POST /platform-api/v1/points/grant`：正整数 `amount`、`reason`、`platform_user_id`、稳定的 `idempotency_key`。
- `POST /platform-api/v1/points/consume`：同上，用于训练营奖励撤回；积分不足时保留异常记录，不伪造成功。
- 结果包含 `transaction_uuid`、`amount`、`balance_after`、`idempotency_key`；客户端核验响应关联后再完成本地记录。
- 签名继续使用现有 Ed25519 / POINTS-SIGN-V1；平台用户标识继续使用七位补零 ID，不切换绑定标识。

**当前限制：**公开契约没有训练营可用的通用流水查询。仅发现 3D 农场专用 `/integrations/3dfarm/users/{email}/transactions`，不复用其他平台的集成密钥。个人页面明确标记「训练营记录」，商城兑换、退款和其他平台记录通过「商城记录」进入商城查看。不能将本地奖励列表当作完整中央账本，也不能通过余额差推算消费。

后续中央接口需要提供：按已认证平台绑定查询当前用户完整流水，稳定分页、来源、收入/消费/退款/调整类型、时间、变动前后余额与关联订单；确认契约后再接入，不预设未存在的路径。

## 上线顺序

1. 常规数据库备份后，先执行 `python scripts/migrate/migrate_78_points_rewards.py` 查看 DDL；确认目标库后使用 `--apply` 建立四张表。迁移可重复执行，不生成奖励、不回填历史数据。
2. 发布后端与前端。保留既有 `POINTS_CENTER_ENABLED`、签名配置、商城回调地址；核实当前平台具有 `platform.points.grant` 与 `platform.points.consume` 权限。
3. 配置 `POINTS_REWARDS_ENABLED=true`，重启应用；原营期调度器每五分钟进行校验和重试。若禁用了 `CAMP_SCHEDULER_ENABLED`，需以独立调度运行 `python scripts/run_points_rewards.py`。
4. 管理员按实际政策新建规则。默认没有示例分值或已启用规则；只接受当前或未来生效时间，不追溯赠送过去积分。版本生效时间不得早于上一版本。
5. 先用获准的测试账号核实真实签名授权与余额响应，再核实一笔受控发放及撤回。当前开发检查没有操作真实积分。

功能开关关闭时不会读取奖励表或运行奖励任务。关停后保留记录；再次启用会继续处理待到账事件，不要删除队列或更换幂等键。归档营限制人工写入，已审批的待到账发放继续完成。
